Síntesis e instalación de la imagen Yocto del sistema de control de acceso

Proyecto 1 · Taller de Sistemas Embebidos · Instituto Tecnológico de Costa Rica · II Semestre 2026

Isaac Vanderlucht López (Rol A) · Daniel Chavarría García (Rol B)

Versión del 2026-10-04

1. Alcance y resultado

Este documento describe, paso a paso, cómo generar desde cero la imagen de Linux a la medida del sistema de control de acceso con Yocto Project, y cómo instalarla en una Raspberry Pi 4. Al terminar, la placa arranca sola el servicio acceso-control, que captura video de una cámara USB, graba la evidencia, transmite en vivo al puesto de vigilancia, lee credenciales QR y acciona un buzzer por PWM.

Se generan dos imágenes desde la misma capa (meta-acceso):

ImagenUsoTamaño (.wic.bz2)
acceso-imageEntrega. Sin contraseña vacía ni herramientas de diagnóstico. Es la que documenta este tutorial.159 MB
acceso-image-devDesarrollo y mediciones. Hereda de la anterior y agrega root sin contraseña por SSH, v4l-utils, videotestsrc y x264enc.162 MB
Estado de la validación

Validado el 2026-10-05 en un contenedor Ubuntu 26.04.1 limpio hasta la simulación completa de la compilación (bitbake -n acceso-image: 7623 tareas, sin errores). Falta ejecutar la compilación completa y medir su tiempo (requisito RNF-5, ítem G4).

Ubuntu nativo, no WSL2

El proyecto empezó en WSL2 sobre Windows y se migró a Ubuntu nativo. Este tutorial describe solo el host nativo.

3.2 Paquetes

Es la lista oficial de Yocto para Ubuntu con dos cambios:

  • liblz4-tool ya no existe con ese nombre en Ubuntu reciente: se llama lz4. Si se copia la lista literal de la documentación de Yocto, apt responde que no encuentra el paquete.
  • Se agrega bmap-tools, que sirve para grabar la microSD (sección 8).
Host

    git iputils-ping libacl1 lz4 locales python3 python3-git python3-jinja2 \
    python3-pexpect python3-pip python3-subunit socat texinfo unzip wget \
    xz-utils zstd bmap-tools
sudo locale-gen en_US.UTF-8
No hace falta desactivar la restricción de user namespaces

Desde Ubuntu 24.04 el sistema restringe los user namespaces sin privilegios (kernel.apparmor_restrict_unprivileged_userns = 1), y circula la recomendación de desactivarla para compilar con Yocto. En este proyecto no fue necesario: la restricción quedó activa, sin archivos en /etc/sysctl.d/, y las compilaciones terminan sin errores.

5. Iniciar el entorno de compilación

El script crea build/ la primera vez, con un local.conf y un bblayers.conf de plantilla que se reemplazan en el paso 6. Encuentra BitBake solo porque está en layers/bitbake, al lado de openembedded-core.

Host, desde ~/proyecto-acceso
source layers/openembedded-core/oe-init-build-env build
Mensajes normales en la primera ejecución

La primera vez el script avisa "You had no conf/local.conf file", lo mismo para bblayers.conf, y dice que es la configuración por omisión de openembedded-core. No es un error: son las plantillas que el paso 6 reemplaza. Al terminar, la terminal queda dentro de build/.

En cada terminal nueva

El source hay que repetirlo en cada terminal antes de usar bitbake. Si se olvida, bitbake responde con código 127 (comando no encontrado).

6. Configurar el build

6.1 bblayers.conf

Rutas relativas a ${TOPDIR} (el directorio build/), para que no dependan del nombre de usuario.

Host: reemplazar build/conf/bblayers.conf
cat > conf/bblayers.conf << 'EOF'
POKY_BBLAYERS_CONF_VERSION = "2"

BBPATH = "${TOPDIR}"
BBFILES ?= ""

BBLAYERS ?= " \
  ${TOPDIR}/../layers/openembedded-core/meta \
  ${TOPDIR}/../layers/meta-yocto/meta-poky \
  ${TOPDIR}/../layers/meta-raspberrypi \
  ${TOPDIR}/../layers/meta-openembedded/meta-oe \
  ${TOPDIR}/../layers/meta-openembedded/meta-python \
  ${TOPDIR}/../layers/meta-openembedded/meta-multimedia \
  ${TOPDIR}/../layers/meta-openembedded/meta-networking \
  ${TOPDIR}/../layers/meta-acceso \
  "
EOF

meta-oe y meta-python son necesarias (OpenCV y PyGObject). meta-multimedia y meta-networking están porque con ellas se compilaron las imágenes del proyecto; no se verificó si se pueden quitar.

Verificación:

bitbake-layers show-layers

6.2 local.conf

La configuración completa está versionada en la capa. Se copia tal cual:

Host, desde build/
cp ../meta-acceso/conf/local.conf.sample conf/local.conf

Qué hace cada parte relevante:

LíneaPor qué
MACHINE = "raspberrypi4-64"Destino de 64 bits. El MACHINE ??= "qemux86-64" anterior viene de la plantilla de Poky: ??= es un valor por omisión débil, y la asignación posterior lo sobrescribe.
DISTRO = "poky", INIT_MANAGER = "systemd"La aplicación corre como servicio de systemd, con reinicio automático y cierre ordenado del MP4.
IMAGE_FSTYPES = "wic.bz2 wic.bmap"Imagen de tarjeta comprimida y su mapa de bloques para bmaptool.
DISTRO_FEATURES:append = " gobject-introspection-data"
MACHINE_FEATURES:append = " qemu-usermode"		Sin los datos de introspección, PyGObject no ve GStreamer (gi.require_version("Gst") falla). qemu-usermode es lo que permite generarlos al compilar en forma cruzada.
PACKAGECONFIG:pn-opencv = "python3 png jpeg"OpenCV con enlaces de Python, para leer los QR.
RPI_EXTRA_CONFIG = "dtoverlay=pwm,pin=18,func=2\ndtparam=audio=off"PWM de hardware en GPIO 18 para el buzzer. Debe estar en local.conf (ver problema 1 en la sección 12).
RPI_KERNEL_DEVICETREE_OVERLAYS:append = " overlays/pwm.dtbo overlays/pwm-2chan.dtbo"Sin esto el overlay no se copia a /boot/overlays/ (problema 1).
ENABLE_UART = "1", GPU_MEM = "128"Consola serie y memoria para el bloque de video.
LICENSE_FLAGS_ACCEPTED += "synaptics-killswitch"Firmware WiFi de la placa, que la imagen base arrastra.
LICENSE_FLAGS_ACCEPTED += "commercial"
PACKAGECONFIG:append:pn-gstreamer1.0-plugins-ugly = " x264"		x264enc, solo para la imagen de desarrollo (comparación de CPU, ítem C2). Ver problema 3.
DL_DIR y SSTATE_DIR en ${TOPDIR}/../Descargas y caché fuera de build/: se pueden reutilizar si se borra el build.
BB_NUMBER_THREADS = "2"
PARALLEL_MAKE = "-j 2"		Ver la nota siguiente.
El paralelismo depende del hardware

Los valores en 2 corresponden a 8 GB de RAM, 4 núcleos y 4 GB de swap. Con más paralelismo, compilaciones grandes como OpenCV o LLVM pueden agotar la memoria y el OOM killer termina el build. En un equipo con más RAM se pueden subir (como guía, ~2 GB de RAM por tarea paralela).

7.3 Compilar

Host, desde build/ (con el entorno iniciado)
bitbake acceso-image

La primera compilación descarga todas las fuentes y compila la cadena de herramientas, el kernel, GStreamer, OpenCV y el resto de la imagen: son más de 7600 tareas y toma varias horas. Las compilaciones siguientes reutilizan el sstate y tardan minutos.

Pendiente: tiempo de una compilación desde cero

No está medido en el host actual. Como referencia histórica (en WSL2, con 2 hilos), la imagen base tardó unas 6 h y OpenCV unas 4 h. La cifra real saldrá de la validación G4.

Imagen de desarrollo

Para mediciones y desarrollo: bitbake acceso-image-dev. Permite entrar por SSH como root sin contraseña y actualizar los módulos de Python con scp + systemctl restart acceso-control sin recompilar. No debe usarse como imagen de entrega.

7.4 Resultado

Host, desde build/
ls -lLh tmp/deploy/images/raspberrypi4-64/acceso-image-raspberrypi4-64.rootfs.wic.*

Archivos a usar: acceso-image-raspberrypi4-64.rootfs.wic.bz2 (~159 MB) y acceso-image-raspberrypi4-64.rootfs.wic.bmap. Los nombres sin fecha son enlaces simbólicos a la última compilación; por eso el tamaño se consulta con ls -L, que sigue el enlace.

La compilación también genera el SBOM en formato SPDX 3.0.1 (tmp/deploy/spdx/3.0.1/), por imagen, rootfs y paquete.

8. Grabar la microSD

  1. Insertar la microSD en el host e identificar su dispositivo: 
    lsblk -d -o NAME,SIZE,TYPE,TRAN,MODEL
  2. Desmontar sus particiones si el escritorio las montó solo (reemplazar sdX): 
    sudo umount /dev/sdX?*
  3. Grabar con bmaptool, que usa el mapa de bloques y salta los bloques vacíos:
    Host, desde build/tmp/deploy/images/raspberrypi4-64/
    sudo bmaptool copy --bmap acceso-image-raspberrypi4-64.rootfs.wic.bmap \
    acceso-image-raspberrypi4-64.rootfs.wic.bz2 /dev/sdX
sync
Elegir bien el dispositivo

bmaptool sobrescribe el dispositivo completo sin preguntar. Confirmar con el tamaño y la columna TRAN (usb o mmc) que /dev/sdX es la microSD y no un disco del host.

9.2 Qué debe pasar solo

No hace falta ningún paso manual. La configuración (/etc/acceso/acceso.conf) viene en la imagen y systemd arranca el servicio acceso-control. El destino del video no se configura: la placa transmite a la computadora que se conecta a su canal de comandos (sección 10).

9.3 Acceso a la placa

Pendiente: acceso de root en la imagen de entrega

La imagen de entrega quitó la contraseña vacía y el login de root sin credencial, pero no define otra forma de entrar, así que lo más probable es que root quede bloqueado por SSH. Opciones en evaluación: dejarlo bloqueado y documentar el acceso por consola serie (la imagen habilita la UART con ENABLE_UART), fijar una contraseña con EXTRA_USERS_PARAMS, o autenticar por llave. Falta decidir cuál y probarla en la placa.

Con la imagen de desarrollo, el acceso es ssh root@<IP-de-la-placa> sin contraseña.

10. Computadora del vigilante

Es otra computadora en la misma red. No usa Yocto. Paquetes en Ubuntu:

Computadora del vigilante
sudo apt install python3-tk python3-opencv gstreamer1.0-tools \
    gstreamer1.0-plugins-good gstreamer1.0-plugins-bad gstreamer1.0-libav

Desde una copia del repositorio, cualquiera de los dos clientes:

# Interfaz gráfica
python3 app/scripts/puesto-vigilancia.py --ip <IP-de-la-placa>

# Consola
python3 app/scripts/vigilancia.py --ip <IP-de-la-placa>

Al conectarse al canal de comandos (TCP 5001), la placa redirige el video (RTP/UDP 5000) a la IP de esa computadora y se abre la ventana del video. Si no aparece imagen, revisar que el firewall de la computadora del vigilante permita UDP 5000.

12. Problemas conocidos

Todos aparecieron durante el proyecto y ya están resueltos en la configuración de este tutorial. Se documentan porque fallan en silencio o con mensajes engañosos.

1. El buzzer no suena y /sys/class/pwm/ está vacío

meta-raspberrypi despliega solo los overlays de una lista explícita (RPI_KERNEL_DEVICETREE_OVERLAYS), y pwm.dtbo no está en ella. El dtoverlay=pwm de config.txt se ignora sin ningún error. Solución: el :append de local.conf (sección 6.2).

Además, RPI_EXTRA_CONFIG tiene que estar en local.conf. La consume la receta rpi-config, que genera config.txt y solo ve la configuración global. Una asignación dentro de la receta de la imagen no la alcanza. Se verifica con: 

bitbake -e rpi-config | grep ^RPI_EXTRA_CONFIG=

2. PyGObject no encuentra GStreamer

Sin gobject-introspection-data en DISTRO_FEATURES, la imagen no lleva los .typelib y gi.require_version("Gst", "1.0") falla. Solución: sección 6.2.

3. x264enc no existe en la imagen de desarrollo

x264 tiene la marca de licencia commercial. Sin LICENSE_FLAGS_ACCEPTED += "commercial", el PACKAGECONFIG que lo activa se ignora en silencio y el elemento no aparece.

4. La imagen sale con una versión vieja de la aplicación

La receta usa la copia de meta-acceso/.../files/, no app/. Solución: ./scripts/sincronizar-receta.sh antes de cada bitbake (sección 7.1).

5. Could not inherit file al seguir tutoriales de otras versiones

En wrynose las clases están repartidas en tres carpetas con reglas distintas: classes/ y classes-global/ se pueden poner en INHERIT de local.conf; classes-recipe/ solo con inherit dentro de una receta. Ejemplo: INHERIT += "cve-check" falla porque esa clase ya no existe en wrynose, y INHERIT += "sbom-cve-check" también, porque está en classes-recipe/. Quien siga una guía de Scarthgap va a intentar INHERIT y va a fallar las dos veces.

En wrynose el análisis de CVE se activa con un fragmento de configuración, un mecanismo nuevo de Yocto 5.x. Hay dos formas equivalentes:

En build/conf/local.conf
OE_FRAGMENTS += "core/yocto/sbom-cve-check"
O desde la consola, con el entorno iniciado
bitbake-config-build enable-fragment core/yocto/sbom-cve-check

La configuración de este tutorial no lo activa: el cruce automático de CVE queda pendiente (sección 13). El SBOM SPDX sí se genera (sección 7.4).

6. Nombres de paquete del host

liblz4-tool no existe en Ubuntu reciente: usar lz4 (sección 3.2).

13. Pendientes

  • G4 / RNF-5: ejecutar este tutorial completo en una máquina limpia, sin downloads/ ni sstate-cache/, y anotar el tiempo total.
  • Acceso a la imagen de entrega: decidir y probar cómo se entra a la placa (sección 9.3).
  • Capas opcionales: verificar si meta-multimedia y meta-networking se pueden quitar de bblayers.conf.
  • Imagen sin gráficos: la imagen lleva gstreamer1.0-plugins-base-opengl, -ximagesink y -xvimagesink en un sistema sin pantalla, porque no se quitaron opengl, wayland ni x11 de DISTRO_FEATURES.
  • CVE: activar el fragmento core/yocto/sbom-cve-check (problema 5), compilar y revisar el informe de vulnerabilidades.
